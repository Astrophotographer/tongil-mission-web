# 통일탐방 미니 — 서비스 기획서

## 1. 목적

통일교육 현장 탐방을 준비하는 교사·강사·대학생이 **탐방 수업 초안**을 빠르게 만들고, 통일 관련 **주장·질문을 짧게 팩트체크**할 수 있도록 돕는 원페이지 웹 서비스입니다.

## 2. 타겟 사용자

| 구분 | 설명 |
|------|------|
| 주 사용자 | 통일교육·현장체험 수업을 기획하는 **교사·강사** |
| 부 사용자 | 탐방 프로그램을 설계하는 **대학생·교육 실습생** |
| 사용 맥락 | 수업 전 탐방지·학습목표·현장미션 아이디어가 필요할 때, 또는 수업·토론 중 나온 통일 관련 주장을 간단히 검증할 때 |

## 3. 페이지 구성 (4개 섹션)

원페이지(`index.html`) + 상단 앵커 메뉴로 이동합니다.

| 섹션 | ID | 기능 |
|------|-----|------|
| **소개** | `#intro` | 서비스 가치 한 줄, 탐방·팩트체크로 이동하는 CTA |
| **탐방 AI 추천** | `#trip` | 날짜·출발지·일정·대상 입력 → AI 탐방 수업안·주변 장소 표시 |
| **팩트체크** | `#factcheck` | 질문/주장 입력(예시 버튼) → AI 판정·근거 요약 |
| **이용 안내 / FAQ** | `#faq` | API 키·실패 안내·주의사항 |

반응형: 모바일에서 햄버거 메뉴, 폼·결과 영역이 깨지지 않도록 구성합니다.

## 4. 기능 A — 탐방 AI 추천

### API

- **엔드포인트:** `POST /api/trip_recommend`
- **구현:** `api/trip_recommend.py`

### 입력 (필수)

| 필드 | 설명 |
|------|------|
| `date` | 탐방일 (`YYYY-MM-DD`) |
| `origin` | 출발지 (텍스트) |
| `schedule` | 일정 (`half` / `full` / `multi` 등) |
| `audience` | 대상 요약 (학년·인원 등) |

### 처리 파이프라인

```text
사용자 입력
  → 1) LLM(Cody): 탐방지·학습목표·현장미션·**시간대별 코스(timeline)**·nearby_area JSON 생성
  → 2) Kakao Local API: nearby_area 기준 맛집·주변지 검색
       (실패 또는 0건 → 빈 목록, 탐방 본문 생성은 계속)
  → 3) LLM(Cody): 장소 검색 결과를 반영한 Markdown 탐방 수업안(시간대별 코스 포함)
  → JSON 응답 → 화면 카드·본문 렌더
```

기록: 탐방·팩트체크 성공 시 `kind=trip|fact_check`(검색)와 문의(`inquiry`)가 모두 `/api/save_result` → n8n → 시트로 저장됩니다.

### 출력 (화면)

- 추천 탐방지, 추천 이유
- **시간대별 탐방 코스** (`timeline`: 시각·장소·활동)
- 학습목표·현장미션 목록
- 주변 맛집·장소 목록 (Kakao 성공 시)
- Markdown 형식 수업안 본문

### 실패·예외 처리

| 상황 | 사용자 안내 |
|------|-------------|
| 필수값 누락 | 「필수값을 입력하세요」 |
| LLM 4xx/5xx·타임아웃 | 「잠시 후 다시 시도하세요」 |
| **Kakao Local 실패·0건** | 「주변 장소 정보를 불러오지 못했습니다」(또는 동등 경고) — **탐방 본문은 표시** |
| 요청 처리 중 | 「응답을 기다리는 중…」 |

## 5. 기능 B — 팩트체크

### API

- **엔드포인트:** `POST /api/fact_check`
- **구현:** `api/fact_check.py`

### 입력

| 필드 | 설명 |
|------|------|
| `question` | 확인할 주장·질문 (필수) |

클라이언트에서 예시 문장 버튼으로 입력란을 미리 채울 수 있습니다.

### 처리

- 동일 Cody 호환 LLM으로 짧은 **판정·근거 요약** 생성
- koreaboard의 보드·차트·용어사전 전체 파이프라인은 이식하지 않음

### 출력

- 팩트체크 결과 텍스트 영역

### 실패·예외 처리

| 상황 | 사용자 안내 |
|------|-------------|
| 빈 입력 | 「필수값을 입력하세요」 |
| API 오류·타임아웃 | 「잠시 후 다시 시도하세요」 |
| 요청 처리 중 | 「응답을 기다리는 중…」 |

## 6. 테스트 시나리오

| # | 유형 | 기능 | 조작 | 기대 결과 |
|---|------|------|------|-----------|
| 1 | **정상** | 탐방 | 필수 4항목 입력 후 「추천 받기」 | 로딩 문구 후 탐방지·**시간대별 코스**·목표·미션·(가능 시) 주변 장소·수업안 표시 |
| 2 | **정상** | 팩트체크 | 질문 입력 또는 예시 클릭 후 제출 | 판정·근거 요약 표시 · 시트에 `팩트체크(검색)` 행 추가(웹훅 설정 시) |
| 3 | **빈 입력** | 탐방 | 일부 필드 비운 채 제출 | 「필수값을 입력하세요」, 결과 영역 비움 |
| 4 | **빈 입력** | 팩트체크 | 빈 질문 제출 | 「필수값을 입력하세요」 |
| 5 | **긴 입력(정상)** | 팩트체크 | 질문란에 약 3,000자(예: 짧은 문장 반복) 입력 후 제출 | 「응답을 기다리는 중…」 후 판정·근거 요약 표시(또는 LLM이 응답하면 정상 결과). 프론트는 길이로 막지 않음 |
| 6 | **긴 입력(타임아웃)** | 탐방/팩트체크 | 약 8,000자 이상 극단 입력 또는 LLM·서버 응답이 약 45초를 넘는 상황 재현 | 로딩 후 「잠시 후 다시 시도하세요」(네트워크/LLM/Serverless 타임아웃). 결과 영역은 성공 본문을 채우지 않음 |
| 7 | **API 오류** | 탐방/팩트체크 | 서버 오류 또는 키 미설정 환경 | 「잠시 후 다시 시도하세요」 등 오류 안내 |
| 8 | **Kakao 경고** | 탐방 | Kakao 키 없음·API 실패·검색 0건 | 주변 장소 경고 + **탐방 본문은 계속 표시** |

### 긴 입력 재현 메모

- 팩트체크: `question`에 `"통일교육. " * 500` 등으로 수천 자 구성(브라우저 개발자 도구 콘솔 또는 붙여넣기).
- 탐방: `destination`·학습 관련 자유 텍스트가 있는 필드를 길게 채우거나, API에 직접 `POST`로 본문을 키워 동일 타임아웃 경로를 확인.
- 서버 LLM 호출 타임아웃은 `api/_llm.py`의 약 **45초**. 초과·네트워크 오류 시 UI는 「잠시 후 다시 시도하세요」.
- 기록 웹훅(`save_result`)은 시트용으로 `input` 2,000자·`summary` 4,000자로 잘라 전달(화면 표시와 별개).

## 9. 지연·응답 개선 옵션(설계)

현재는 요청마다 LLM(+Kakao)을 **동기**로 호출합니다. 병목은 주로 LLM 왕복(수 초~수십 초)입니다. 아래는 도입을 검토할 수 있는 개선안과 트레이드오프입니다.

| 개선안 | 요지 | 속도 | 비용 | 단점·주의 |
|--------|------|------|------|-----------|
| **응답 캐싱** | 동일·유사 입력(해시 키)의 LLM/Kakao 결과를 단기 저장(메모리·KV·시트) | 반복 질문 시 체감 크게 개선 | LLM 호출 감소 | 최신성↓, 개인·교육 맥락이 섞이면 캐시 키 설계 필요 |
| **타임아웃 조정** | `api/_llm.py` ~45초·Serverless maxDuration을 짧게/길게 | 짧게: 실패 빨리 안내 / 길게: 긴 입력 성공률↑ | 긴 타임아웃은 점유·과금↑ | 짧게 하면 긴 입력(#6) 실패↑ |
| **프롬프트·모델 축소** | 짧은 시스템 프롬프트, 더 빠른/저가 모델 | 보통 개선 | 비용↓ | 품질·판정 깊이 저하 가능 |
| **Kakao 병렬화** | LLM과 장소 검색을 동시에 | 탐방 총 대기↓ | 변화 적음 | 실패 분기·부분 결과 UX 유지 필요 |
| **비동기·백그라운드** | 즉시 `job_id` 반환 → 폴링/웹훅으로 결과 전달 | 체감 TTFB↓, UX는 “생성 중” | 큐·저장소 비용 | 구현 범위 큼(상태 저장, 만료, 재시도) |
| **스트리밍** | LLM 토큰 스트리밍을 UI에 표시 | 체감 대기↓ | 유사 | Serverless/프록시 스트리밍 지원·프론트 파서 필요 |

**현재 미션 범위에서의 선택:** 동기·단순 구조를 유지하고, 운영 단계에서 필요 시 **캐싱 + 타임아웃 튜닝**을 우선 검토합니다. 비동기 잡은 트래픽·대기 불만이 커질 때 도입합니다.

## 10. API 키 유출 대응 절차

키가 채팅·커밋·스크린샷·로그에 노출됐거나 의심될 때 **즉시** 아래를 따릅니다. (값을 문서·이슈에 다시 붙이지 않음)

### 10.1 즉시 폐기·교체

1. **LLM** 콘솔에서 해당 API 키 **폐기(revoke)** 후 새 키 발급  
2. **Kakao Developers**에서 REST/JS/Native 키 재발급 또는 앱 키 교체, JS 키 도메인 허용 목록 재확인  
3. (사용 중이면) **n8n Webhook URL** 재생성·워크플로 재활성화, 구 URL 무효화  
4. Vercel → **Environment Variables**에서 `LLM_API_KEY`, `KAKAO_*`, `WEBHOOK_URL`을 **새 값으로 교체** (Production / Preview / Development)  
5. **재배포** (`Redeploy` 또는 `npx vercel deploy --prod`) 후 탐방·팩트체크 1회씩 확인  

### 10.2 재발 방지 체크리스트

- [ ] `.env` / `.env.local`이 `.gitignore`에 포함되어 있고 git에 올라가지 않음  
- [ ] README·`docs/`·이슈·PR·스크린샷에 **실값 없음** (이름만 표기)  
- [ ] 프론트 JS에 시크릿을 넣지 않음 (`KAKAO_JS_KEY`만 공개용으로 `/api/public_config` 경유)  
- [ ] Vercel 변수를 **Sensitive**로 두고, 채팅에 붙여 넣지 않음  
- [ ] 유출 의심 시 키를 “가리고 재사용”하지 말고 **무조건 재발급**  

### 10.3 로그 조사 방법

| 확인처 | 목적 |
|--------|------|
| GitHub → Commits / Secrets scanning | 과거 커밋· fort에 키가 남았는지 |
| Vercel → Deployments / Runtime Logs | 요청·오류에 키가 찍히지 않는지(앱은 키를 로그에 남기지 않음) |
| 브라우저 Network | 응답에 `api_key` 등이 노출되지 않는지 |
| LLM·Kakao 콘솔 사용량/감사 | 이상 호출 시각·IP·쿼터 급증 |

의심 구간이 있으면 **폐기 → 교체 → 재배포**를 마친 뒤, 구 키가 있던 커밋이 있다면 히스토리에서 제거하거나 저장소를 private으로 두고 키는 이미 폐기된 것으로 간주합니다.

## 11. 프레임워크 도입 비교 · 마이그레이션

미션 제약은 **바닐라 HTML/CSS/JS**이므로 현재는 프레임워크를 쓰지 않습니다. 이후 확장 시 참고용 비교입니다.

| 항목 | **현재 (Vanilla + Vercel Python `api/`)** | **Next.js (App Router)** | **Vite + React** |
|------|-------------------------------------------|--------------------------|------------------|
| 장점 | 빌드 최소, 제출·리뷰 단순, 미션 제약 충족 | SSR/라우팅·API Route 일체, 생태계 | SPA 개발 속도, 컴포넌트 재사용 |
| 단점 | 상태·라우팅 직접 관리, 규모 확장 시 비용↑ | 학습·설정 비용, 미션 “프레임워크 금지”와 충돌 | 별도 API 호스팅 설계 필요 |
| **빌드** | 정적 파일 그대로 (번들 없음) | `next build` · Node 런타임 | `vite build` → `dist/` |
| **라우팅** | `index.html` 앵커·단일 페이지 | 파일 기반 `/app` 라우트 | React Router 등 추가 |
| **API** | `api/*.py` Serverless | Route Handlers / Server Actions (보통 TS) | 기존 Python `api/` 유지 또는 BFF 재작성 |
| **배포** | Vercel Framework **Other** | Vercel **Next.js** 프리셋 | 정적 + Functions 또는 별도 백엔드 |
| **변경 범위(대략)** | — | `index.html`/`js/*` → React 컴포넌트, `api/` Python→TS 또는 rewrite, CSS 모듈화, env·미들웨어 | 프론트만 이관 시 `api/`는 유지 가능, 진입점·에셋 경로·CORS 점검 |
| **마이그레이션 전략** | — | 1) 정적 섹션을 페이지로 이전 2) fetch 호출을 hooks로 이전 3) Python API를 Route로 포팅 또는 프록시 4) 프리셋 바꿔 재배포·E2E | 1) Vite 스캐폴드 2) 섹션별 컴포넌트화 3) `vercel.json` 정적 출력 연동 4) API 경로 호환 유지 |

**권장:** 미션·운영 단순함이 우선이면 **현 스택 유지**. 다중 페이지·인증·복잡한 UI가 필요해지면 Next.js를 우선 후보로 두고, 위 표의 빌드·라우팅·배포 항목을 체크리스트로 삼아 단계 이전합니다.
